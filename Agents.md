# ТЗ для Codex

## Проект: ИС учета покупки посадочного материала

### 1. Общая цель проекта

Разработать с нуля настольное приложение для учета закупки посадочного материала с базой данных PostgreSQL и интерфейсом на Python.

Система должна позволять:

* вести справочник поставщиков;
* вести справочник посадочного материала (цветов);
* регистрировать договоры на оформление;
* создавать и учитывать заказы на поставку посадочного материала;
* рассчитывать стоимость заказов и итоговую стоимость по договорам с учетом коэффициента;
* разграничивать доступ по ролям;
* формировать отчеты за выбранный период.

## 3. Предметная модель

В системе должны быть 4 основные таблицы:

1. **suppliers** — поставщики
2. **flowers** — виды посадочного материала
3. **contracts** — договоры
4. **purchase_orders** — заказы на поставку

### Важное допущение

Так как таблица **«Заказчик»** исключена, в таблице `contracts` нужно хранить поля:

* `customer_name`
* `customer_phone`
* `customer_email`

Это позволит не нарушать логику предметной области.

## 4. Структура базы данных

### 4.1. Таблица `suppliers`

Хранит данные о поставщиках.

Поля:

* `id` — PK, целое автоинкремент
* `name` — наименование поставщика, обязательное поле
* `contact_person` — контактное лицо
* `phone` — телефон
* `email` — email
* `address` — адрес
* `inn` — ИНН, если нужен
* `is_active` — активен/неактивен
* `created_at`
* `updated_at`

Ограничения:

* `name` не пустое
* `email` может быть nullable
* `phone` может быть nullable

---

### 4.2. Таблица `flowers`

Хранит каталог посадочного материала.

Каждая запись привязывается к поставщику, чтобы в системе было понятно, у кого закупается конкретная позиция.

Поля:

* `id` — PK
* `supplier_id` — FK → `suppliers.id`
* `name` — название цветка
* `variety` — сорт
* `color` — цвет
* `unit` — единица измерения, например `шт`, `кассета`, `лоток`
* `purchase_price` — закупочная цена за единицу
* `min_batch` — минимальная партия
* `season` — сезонность
* `notes` — примечание
* `is_active`
* `created_at`
* `updated_at`

Ограничения:

* `purchase_price > 0`
* `min_batch > 0`
* `supplier_id` обязателен

---

### 4.3. Таблица `contracts`

Хранит договоры на выполнение работ.

Так как отдельной таблицы заказчиков нет, сведения о заказчике входят прямо в договор.

Поля:

* `id` — PK
* `contract_number` — номер договора, уникальный
* `contract_date` — дата договора
* `customer_name` — наименование заказчика
* `customer_phone` — телефон заказчика
* `customer_email` — email заказчика
* `object_name` — название объекта оформления
* `object_address` — адрес объекта
* `start_date` — дата начала работ
* `end_date` — дата окончания работ
* `price_coefficient` — коэффициент для расчета стоимости, по умолчанию `1.00`
* `status` — статус договора
  допустимые значения: `draft`, `active`, `completed`, `cancelled`
* `notes`
* `created_at`
* `updated_at`

Ограничения:

* `contract_number` уникален
* `price_coefficient > 0`
* `customer_name` обязательно
* `object_name` обязательно

---

### 4.4. Таблица `purchase_orders`

Хранит заказы на поставку посадочного материала в рамках договора.

Поля:

* `id` — PK
* `contract_id` — FK → `contracts.id`
* `flower_id` — FK → `flowers.id`
* `quantity` — количество
* `unit_price_snapshot` — цена за единицу на момент создания заказа
* `line_amount` — сумма без коэффициента
* `order_date` — дата заказа
* `planned_delivery_date` — плановая дата поставки
* `actual_delivery_date` — фактическая дата поставки
* `status` — статус заказа
  допустимые значения: `created`, `approved`, `ordered`, `delivered`, `cancelled`
* `notes`
* `created_at`
* `updated_at`

Ограничения:

* `quantity > 0`
* `unit_price_snapshot > 0`
* `contract_id` обязателен
* `flower_id` обязателен

Бизнес-логика:

* `unit_price_snapshot` должен автоматически подставляться из `flowers.purchase_price` при создании заказа;
* `line_amount = quantity * unit_price_snapshot`;
* итоговая стоимость заказа с учетом коэффициента договора вычисляется в запросах и отчетах:

  `final_amount = line_amount * contracts.price_coefficient`

### 8.4. Аналитик / Бухгалтер

Права:

* `suppliers` — просмотр
* `flowers` — просмотр

## 10. Проверки и валидация

Codex должен реализовать валидацию:

* обязательные поля не могут быть пустыми;
* цена и количество должны быть больше нуля;
* коэффициент должен быть больше нуля;
* `end_date` не может быть раньше `start_date`;
* `actual_delivery_date` не может быть раньше `order_date`;
* номер договора должен быть уникальным;
* удаление записи, на которую есть ссылки, должно корректно обрабатываться.

Ошибки нужно выводить в понятном виде через диалоговые окна.

## 12. Поведение приложения

### 12.1. Авторизация

* пользователи и роли описываются в конфиге;
* после входа интерфейс скрывает недоступные разделы;
* кнопки CRUD блокируются по роли.

### 12.2. Работа с данными

* таблицы должны отображаться в `Treeview`;
* формы ввода открываются в модальных окнах;
* после изменения данных таблица обновляется автоматически.

### 12.3. Расчет стоимости

* при создании заказа цена подставляется из цветка;
* при изменении количества пересчитывается сумма;
* отчет должен учитывать коэффициент договора.
